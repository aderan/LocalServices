# LOCOVE-WORKBENCH-UI-REFACTOR

## 1. 目标与完成边界

重构 Locove／洛湾的服务工作台和 macOS 菜单栏快捷体验。用户从菜单栏或工作台找到服务，看到实际状态，直接打开或启动并打开。遇到异常时，从原位置进入对应服务的诊断，了解影响并查看日志或执行适用操作。主窗口与浏览器提供同一套完整工作台。Agent 可用本地结构化接口核验状态，用浏览器复现同一条界面路径。

整体完成包括共享工作台、诊断和菜单栏三个界面，以及浏览器、现有 API／CLI 和原生 App 的验收证据。首轮服务列表是起点。原生安装受平台阻塞时，先完成可独立验收的部分，明确记录真实安装和启动的验收缺口。

## 2. 决策与材料

### 用户已明确的方向

- 视觉参考 Magpie，采用克制的 macOS 工具界面。用户提供 Stitch 的工作台、故障展开、菜单栏三稿作为本轮输入。
- 项目侧栏去掉常驻服务数。项目内有故障或降级时显示提醒。全局「需要处理」仍可集中处理，项目规模可在总览和详情查看。
- 设置和打开主窗口放在各自适用界面的顶部，方便快速进入。
- 设计同时服务 GUI 用户和 Agent。用户要求评估浏览器端口作为真实界面测试入口，并保留可自动核验的操作路径。

### 必读与证据

1. 本文件及[现有契约](../CONTRACTS.md)，重点看 V2.6、V2.7、V2.11、V3.5–V3.7。用户最新明确的修订优先。既有生命周期和安全语义以契约为准，视觉稿里的示例内容以运行事实为准。
2. 三张 Stitch 参考图分别对应[工作台](../research/assets/locove-stitch-workbench/workbench.png)、[故障展开](../research/assets/locove-stitch-workbench/diagnosis.png)和[菜单栏](../research/assets/locove-stitch-workbench/menubar.png)。它们来自 `locove_3`、`locove_1`、`locove_2`。截图随仓可读。导出 HTML 含远程 Tailwind 脚本和静态占位行为，界面用本地资产实现。
3. 按需参考 [Magpie 面板](../research/assets/locove-ui-references/magpie-panel.png)、[仓库品牌图](../../assets/locove-logo.png)、[README](../../README.md)和[已交付的 D1–D5 Goal](locove-foundation-domains-ui-goal.md)。此前的域名和生命周期项目是兼容基线。

### 实施建议

优先保留 AppKit／WKWebView、Python daemon 和共享本地网页，使用「在浏览器中打开」作为辅助入口。使用现有接口做端到端小改动，具体文件拆分和状态更新方式由执行者根据代码决定。单服务项目可合并重复标题，多服务项目保留分组和组操作。菜单栏可用 AppKit popover 实现带搜索的快捷列表，窗口形态与具体控件由原生交互验收决定。

## 4. 推进与验收

| 阶段 | 交付 | 可观察验收 |
|---|---|---|
| W1 共享工作台 | 顶部工具栏、项目导航、统一服务行、搜索与刷新 | 以主窗口最小尺寸 `960 × 600` 和常用宽窗验证。长服务名、地址、状态与操作互不覆盖。设置长诊断在较窄内容区可读。健康或主动停止的项目无常驻数字。搜索和打开／启动并打开可达。键盘焦点、展开态、日志选区、滚动位置跨轮询稳定。 |
| W2 故障路径 | 从服务行和「需要处理」进入对应服务诊断。展示影响与现有可执行动作，按需查看入口、组件、依赖和日志 | 用夹具覆盖可用、主动停止、准备环境、部分可用、启动失败、端口冲突、外部实例、只读观察和 daemon 断连。只读服务可看状态，启动类动作按 daemon 能力显示。现有重试及日志路径可用。浏览器和原生入口都能定位到同一服务。 |
| W3 菜单栏 | 顶部刷新、打开主窗口、设置，快捷定位常用服务与异常，提供打开／启动或进入诊断 | 主要入口可用键盘到达。验证状态刷新、打开主窗口、打开设置、跳转对应诊断、关闭窗口及退出菜单栏。实测安装后由 launchd 启动，原有后台服务继续运行。 |
| W4 集成验收 | 同一浏览器端口与主窗口行为一致，可供用户和 Agent 重复验证 | 全量测试、真实浏览器回归与 macOS 原生冒烟均有证据。验证深链接或等效定位入口、稳定的服务和操作标识、浏览器直接打开及目录选择桥接。业务写操作在独立 daemon 和运行夹具中执行。 |

使用 `python3 -m pytest tests/ -q`、`node scripts/verify_v2_gui.cjs`、`node scripts/verify_d1_browser.cjs <证据目录>` 和 `bash menubar/build.sh` 作为现有入口。V2 GUI 脚本用隔离 daemon 和桩 DOM，D1 用真实 Chromium，原生构建后另验 WKWebView 与 launchd。上轮变更通过 585 项测试及 14 个子测试，本次交接未重跑。若调整脚本加载方式，同步更新[依赖内联脚本的验证器](../../scripts/verify_v2_gui.cjs#L55)。

Agent 使用 `lsctl status --json`、其他支持 JSON 的子命令或受保护的本地 API 验证运行事实，使用浏览器验证真实 DOM 和交互。写操作测试分配独立端口、状态与清单目录、launchd 标签前缀和服务夹具。Docker 场景用 mock 或专用测试环境，隔离 Web 端口本身不会隔离 Docker。浏览器测试继续访问正常的工作台入口。

## 5. 待定扩展

**独立「启动 Colima」按钮已讨论可行性，独立控制接口仍待范围确认。** 现有 [Infrastructure](../../localservices/infrastructure.py#L63) 会在必要依赖预检中恢复既有本机 Colima。本轮先把真实依赖失败、日志和现有服务重试接入诊断。若后续纳入独立动作，建议由共享资源和相关服务诊断调用同一 daemon 能力，按本机 context 判定可用性，以 Docker 引擎实际可达作为成功条件。Lima 残留盘锁需要明确诊断和恢复指引。不得把远程 Docker、重启其他容器、磁盘解锁或升级系统工具隐含进按钮。此决定不阻塞 W1–W4。
