# LOCOVE-FOUNDATION-DOMAINS-UI

## Goal 与完成边界

将现有 LocalServices 演进为 **Locove／洛湾**：用户在统一工作台添加、管理并打开本机项目，可选使用 `buildbase.locove` 这类无端口专属域名访问 Web 服务；架构职责和 UI 支持这一完整流程，已有生命周期、数据保护及 CLI/Skill 能力保持可用。

这是一个完整开发 Goal，包含品牌落地、必要架构调整、通用域名能力、UI 改造及安装/升级/恢复验证。当前交接是**在既有实现上修复 review 问题并完成剩余交付**，执行范围为 §5 的 C1–C5，覆盖 R1–R7 和原 Goal 未完成的验收。复用已验证成果，不重做最初 M1–M3；交付计划或只让 Buildbase 一个地址可访问不代表完成。本次交接仅更新文档，接手者收到启动指令后实际实施。

沿用现行 [CONTRACTS V3.5](../CONTRACTS.md) 及 [域名可选记录](../../artifacts/acceptance-LOCOVE-FOUNDATION-DOMAINS-UI/V35-DOMAIN-OPT-IN-RECORD.md)：默认打开/复制本地直连地址；用户开启域名跳转后使用无端口域名，入口故障时可明确提示并回退直连。域名关闭不表示停掉本地 DNS/代理。无端口要求适用于域名访问，不以本 Goal 早期描述覆盖后续的可选设置。

普通 Web 页面以 `http://<service>.locove` 无端口访问作为基础验收。HTTPS、本地 CA 信任尚未获得单独的范围确认，不将其静默升级为本 Goal 的额外大阶段；若受管应用的必要功能依赖 HTTPS，先明确实际影响与最小增量，再与用户确认受影响的范围，其他工作继续推进。

### 2026-11-04 review 澄清：本地运行与 UI 验收

- 本 Goal 的默认交付为本机 HTTP，不增加证书、CA 信任或 443 监听作为必要步骤。HTTPS 与上云没有必然关系；当前实现的 `auto_https off` 符合基础范围。

## 4. 目标行为与设计要求

### 用户完整流程

打开 Locove／洛湾 → 查看已有项目和真实状态 → 选目录并识别/手工登记服务 → 核对配置与差异 → 启动并等待应用真正就绪 → 默认直连，或启用域名后无端口打开 → 查看日志/依赖或处理故障 → 编辑不改变未编辑的域名来源，移除/恢复时域名和登记一致收敛。

通用能力至少通过 Next 和 Vite 两种不同样例走完。Buildbase 是真实端到端验收样例，不是唯一硬编码目标。

### 架构优化的可观察结果

1. Project、Service、Component 的含义和 ID 用途明确，旧接口通过兼容层继续工作。
2. 运行意图由统一入口修改；恢复/刷新/启停并发不由旧缓存覆盖其他修改。先写能暴露风险的行为测试，再调整。
3. 观测/快照和执行调度职责明确；状态查询不隐式改变用户运行意图，更新/重试仍按既有策略推进。
4. 本地进程、Compose 与项目 busy/health 策略的职责明确；使用确实存在的变化点，不增加只转发调用的空层。
5. 新路由的校验/提交/激活失败可诊断并保持上次有效状态；新的依赖引用和顺序配置明确拒绝未知引用或环。

### 域名与安装

- 新登记通过同一套机制分配和持久化域名；重名在提交前失败，显示名称修改不意外破坏稳定地址。
- 目标组件、打开路径、公开域名、实际端口各自表达；`/zh` 是落点，整个应用路径/脚本/资源都能代理。
- Endpoint 贯穿注册、schema、清单、人工覆盖、diff、导出、归档、恢复、UI/CLI/Skill；恢复时重新检查域名冲突。
- 已确认归属且就绪的外部实例可使用实际端口作为上游；退出或变成未知占用时不得路由到无关程序。
- 服务停止显示准确不可用状态；移除撤销活动路由；恢复、daemon/代理/DNS 重启后能够重建一致配置。
- DNS、入口、路由和应用健康分别观测；80 已占用或权限不足必须显示原因。高端口只能是内部实现，不能作为成功交付的公开回退地址。
- 安装/修复/升级/卸载幂等，只管理自身配置；正常安装不替换全局 DNS、不覆盖用户已有 resolver/hosts/PF 规则。
- `.locove` 是本机命名约定；不需要购买公网域名。提供按需诊断和后缀迁移能力的实现空间。

### UI 与品牌

- 所有主要产品入口清楚呈现 Locove／洛湾；英文品牌与中文名称保持一致，不把底层兼容标识展示为第二套产品身份。
- 紧凑列表直接显示服务名、当前访问模式的地址、真实状态/归属和主要动作；域名开启时呈现无端口地址。收拢重复标题及次要操作。
- 项目/服务、异常、资源、Agent、草稿、恢复管理各有清楚位置，详情承接日志、组件、依赖和配置。
- 保留从添加到运行的完整流程；准备环境、安装/构建、就绪、失败应能区分，断线显示未知而非假装停止。
- 页面更新不打断编辑、焦点、滚动和模态；异步请求不会以旧结果覆盖新状态。键盘/VoiceOver、明暗主题及长名称可用。
- 用官方截图的密度、对齐和主副文本关系指导实现；使用自己的品牌资产，不将旧截图逐像素复制作为验收方式。

本轮 R6 需要交付可见的完整改造：CC Switch 参考用于统一侧栏/页头、当前状态与配置交互；Magpie 参考用于整组紧凑行、细分隔、主副文本、行尾对齐和克制的状态色。具体配色与构图允许执行方选择，但应在工作台主视图、服务详情和设置/草稿组织中形成一致语法，保留明暗主题。建立实际页面前后对照和行为证据，不能把地址 chip、新文案或函数锚点测试当作风格完成证明。

运行中服务一行优先保留主要动作，日志和必要的高频入口有稳定位置，停止/重启/源码等次要操作按交互层级收拢。详情支持用户完成诊断任务，而非把所有技术参数继续挤在首屏。域名诊断说明按故障与设置上下文披露，避免整段 shell 命令长期占据主工作区。
